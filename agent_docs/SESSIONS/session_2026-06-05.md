20. **Design tokens need an in-browser dark-mode readability pass before lock — not just a style-tile check.** The v1.0 style tile passed designer review, but Tony's first real-screen dark-mode visit revealed background/card elevation defect + insufficient `muted-foreground` contrast. **Recon questionnaire / FFM packaging note:** before token "lock", require both: (a) style-tile review (already done), (b) `npm run dev` walkthrough at the major dark surfaces (cards on background, secondary text, form fields with placeholders, borders). The style tile shows tokens in isolation; the dev server shows them in real layout context where elevation/hierarchy issues manifest.
21. **Phase 2 reference PNGs CAN be used as static marketing assets in Phase 1 landing** without crossing the streams. The discipline: static `<Image>` referencing a PNG is a picture, not a build. The line is the moment you write dashboard JSX (tabs, tables, KPI tiles) — that's Phase 2. This nuance worth documenting in the FFM doctrine so future runs don't reflexively forbid the marketing-asset use.
22. **Dead nav links create lying UI even when "kept for visual completeness."** C4 left `/booking`, `/xxx`, `/superadmin-portal` in navbars after route deletion (deferred to C5). The right discipline: navbar nav links should be removed AT THE SAME TIME as route deletion, not deferred to a later cluster. C5 surface and fix worked, but it was a known-broken intermediate state. **Playbook addition:** route deletion checklist should include grep for surviving link sites + delete or surface.
23. **NavbarHome can be a Server Component when it's a marketing nav.** The kit shipped NavbarHome as a `"use client"` component with auth-state logic + user dropdown. For a public marketing nav (no auth-aware UI), there's no need for client state. Phase 1 NavbarHome dropped to Server Component, smaller client bundle, no hydration overhead. **General lesson:** treat `"use client"` as an opt-in cost, not a default. The kit's defaults were overly client-heavy for surfaces that don't need it.
24. **`Logout.tsx` is shaped as `DropdownMenuItem`** — works inside `<DropdownMenu>` only. For a placeholder page with an inline logout button, you have to inline the logout logic (`useAuthStore.getState().logout()` + router push) rather than reuse the component. **Kit improvement candidate for v1.2:** make `Logout.tsx` more flexible (accept render-as prop or return a function instead of JSX).
25. **Complex two-column hero layouts transform at `lg:` (1024px), not `md:` (768px).** The kit handbook / design Rule Zero explicitly says "Tablet (md) is a transition, not a bespoke layout" — but the C5 B-3 first draft engaged the side-by-side transform at md, which broke the visual column at 782px (visual needs more width than tablet provides). **Recon questionnaire / FFM packaging note:** for any complex split hero (copy + visual), bake `lg:` as the default transform breakpoint — `md:` is reserved for textual / size-only transitions (e.g., `md:text-6xl` as a bridge step between mobile and desktop typography). The handbook said it; the JSX initially didn't enforce it. Should be a default pattern in C5 future runs.
26. **Marketing nav and portal nav have DIFFERENT mobile-menu needs — don't conflate them.** Marketing nav (NavbarHome) has real destinations including **Log in** that MUST stay reachable on mobile, so it NEEDS a hamburger. Portal nav (Navbar) for placeholder portals with no Dashboard/Settings/Reports destinations doesn't need one — logo + user menu is honest. The C5 first-pass ruling "no hamburger, drop dead links" was right for the portal nav but wrong for the marketing nav; treating them as the same kind of navbar was the bug. **FFM packaging note:** future runs should distinguish **marketing-nav** (needs mobile menu by default, surface a hamburger; the Log-in link is the critical real destination) from **portal-nav** (mobile menu only if there are real destinations) per screen — recon questionnaire should ask separately.
27. **Server Component navbar with client island hamburger is the right shape.** NavbarHome stays Server Component (no client state for the marketing nav itself — links are static, no auth-aware UI), while a tiny `<MobileNav />` sub-component owns the `useState` for hamburger toggle. Smaller client bundle than making the whole navbar client. Pattern is generally applicable: server shell + client island for any small interactive widget inside an otherwise-static surface.
28. **Theme toggle belongs on EVERY navbar surface — including marketing nav.** Initial NavbarHome shipped without ThemeToggler because the doctrine focus was on auth-aware portal navbars. But theme preference is a UX setting that applies everywhere; a marketing-page visitor should be able to switch themes too without first signing in. **FFM packaging note:** "theme toggle reachable from every navbar" should be a default requirement, not an opt-in per nav variant. Add to recon questionnaire.
29. **For "always visible" controls on mobile, place next to the hamburger, not inside its menu panel.** Theme toggle could have lived inside the MobileNav panel, but that requires opening the menu first to access it. Single-tap reach from collapsed state is better UX. **Pattern:** small interactive widgets that aren't *navigation* (theme toggle, search, user avatar) stay visible at top level on mobile; nav links live behind the hamburger. The line is: navigation belongs in the menu, controls belong outside.
30. **APP_BRIEF env-var names can be stale — recon must read `.env.local.example` AND grep `process.env` in code, not trust doc-specified names.** APP_BRIEF §3 listed `NEXT_PUBLIC_SUPABASE_ANON_KEY` + `SUPABASE_SERVICE_ROLE_KEY` (legacy Supabase naming). Reality: the codebase was already updated to Q4-2025 Supabase naming (`PUBLISHABLE_KEY` + `SECRET_KEY`), and Tony's `.env.local.example` matches the code. APP_BRIEF was the only stale source. Same class of failure as **handbook-is-aspirational** (#meta-lesson) but applied to env vars. **Recon questionnaire addition:** every env-related validation should read `.env.local.example` first and grep `process.env.*` in `src/` to ground truth; never trust doc-specified names. APP_BRIEF should be updated to current names at some point (out of scope for this run).
31. **Turbopack dev mode prints "✓ Ready" BEFORE instrumentation throws propagate — cosmetic ordering, NOT a fail-closed regression.** During C6 G5 proof, Tony's bad-start test showed `✓ Ready in 329ms` followed by the instrumentation error, which initially looked like "server started despite the error." Verification via `curl http://localhost:3000` → connection refused; process gone. So the gate IS fail-closed; the log ordering is just Turbopack reporting its banner optimistically before the throw kills the process. **Lesson for future runs:** when an instrumentation throw is the verification target on Turbopack, do NOT rely on log order alone — verify the process actually died (curl, ps aux, or check that the port stays unbound). Otherwise a real fail-closed looks suspicious.
32. **"Sample-check one primitive then trust the rest" is brittle.** Y4 ruling at C4 Phase A trusted that `button.tsx` cleanliness would predict the rest of `src/components/ui/`. Reality: `dialog.tsx`, `dropdown-menu.tsx`, and `toast.tsx` all had hardcoded numbered colors despite `button.tsx` being clean. SP4 close-out grep (C7) caught it; 5 sites migrated. **Lesson:** when auditing a class of files for a property (e.g., "no numbered colors"), sample-check is **not transitive** — either audit every file, or accept the deferral knowing it's incomplete (with a clear handoff to a later cleanup pass). The C7 ground-truth grep — running the gate's own verification predicate before claiming the gate green — should be a **standard close-out step**, not an afterthought. **FFM packaging:** every gate that has a grep-verifiable predicate gets its grep run at SP-close, not assumed satisfied because a sample passed.
33. **"Marketing nav, no auto-redirect" does NOT mean "no auth state at all" — distinguish routing-behavior decisions from UI-state decisions.** C5 ruling #6 said: authenticated visitor at `/` sees the marketing page, no auto-redirect. I misinterpreted that as "static Server Component with zero auth awareness." The first SP5 continuous-walk caught the stranding: logged-in user navigates back to `/`, has no idea they're logged in, no link to their portal, no logout — fully stuck. **Real distinction:** "no auto-redirect" = don't bounce the user away from `/`. "Auth-aware nav" = reflect their state in the UI so they can navigate. Both can coexist. **Pattern:** marketing nav needs an auth-state-aware right-side region (Avatar dropdown for logged-in / Log in + CTA for logged-out). Treat as a baseline correctness requirement, not a polish item, regardless of phase. **Recon questionnaire:** every public/marketing route should have an auth-state region defined (what shows when logged in vs logged out), not just routing rules.
34. **Continuous-walk SP5 verification catches what piecewise-gate proofs miss.** Each Phase 1 gate (G1-G14) was proven in isolation — tests pass, tokens installed, login redirect works in unit tests, route gates enforce per jest. All the pieces worked. But the FIRST continuous live walk (Tony's SP5 ritual) surfaced the stranded-on-`/` UX bug above — a real correctness failure that no individual gate's grep or unit test would catch. **Lesson:** SP5 is not a formality; it's the only place that catches integration-level UX bugs where the seams between components fail. **FFM packaging:** SP5 verification ritual should explicitly include "navigate between every surface in every auth state" as a step, not just "click the happy path."

**Meta-lesson stands:** Kit handbook is aspirational. 6 bugs + 2 doctrinal drifts + several quality issues caught in single run. Needs v3 reconciliation pass.
